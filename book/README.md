# The Alder Book

Alder is a small, strict language for building server-rendered web
applications. It is designed so that an AI agent (or a person) has exactly
one way to do each thing, and so that the compiler catches the mistakes
that normally show up as a 404, a 500, or a broken form.

This book is the single source of truth for the language. When the language
changes, this book changes first.

## Status

Alder is a design in progress. `alder new <name>` writes a first app, the guestbook of chapter 2, which checks, tests, builds and serves; Alder installs as one binary (a release archive, Homebrew, or a container image for CI) and needs only Go beside it (chapter 1, "Installing"). Three example apps exist, `examples/todos` (chapter 2), `examples/blog` and `examples/workspace` (chapter 14), and all check, build, serve and pass their tests. An app can be built from the command line: `alder new page`, `table`, `form`, `msg` and `capability` write plain, checked Alder with tests that kill its mutants, `alder edit table` changes a table and its migration and lists what the change breaks, `alder fill` fills a typed hole with one expression and writes it only if the app still checks, and `alder new admin` writes an admin of every table, which `alder regen admin` keeps up to date through owned regions; both examples carry one, unedited, and chapter 15 shows every command with a transcript `go test ./book` runs. `alder check`, `alder dump` and `alder build` exist: the to-do app serves, and `alder build` produces a binary that runs it over HTTP against SQLite (chapter 11). `alder run` rebuilds and reloads: save a file and the browser shows the new app, or the compiler's errors (chapter 11). `alder eval` evaluates an expression against the app (chapter 11), and `go test ./book` verifies every Alder block in this book not marked as a fragment: modules and declarations are type-checked (and the modules the tours show piece by piece must equal the examples' files, and chapter 2 must quote every file `alder new` writes, as it writes it), `eval=` and `error=` expressions are evaluated, other expressions are parsed. `alder test` runs the app's tests, each effect test against a fresh in-memory database, a test can replace a capability with a `fake` written in Alder, with tables of its own, and a test can drive the app through an in-memory browser that requests its real routes inside the test's transaction: log in, get a page, submit its forms, click its buttons, and read the page and the session that follow (chapter 10). `alder test --mutate` measures the tests: it compiles every curated, well-typed mutant of the app (a `requires` dropped, a write replaced, an order reversed, …) into one test program, runs the suite once per mutant, and prints the score and each survivor as the test that is missing; `--min R` makes the score a gate in CI (chapter 10, "Mutation testing"; chapter 13 shows how). Both examples run under it: the to-do app's 112 mutants are all killed, and the blog's 182 all but three equivalent ones. The two authorization rules every app with a login needs are declared, not written: `@owner` on a table's column gives it the scoped operations `Db.mine`, `Db.getMine`, `Db.updateMine`, `Db.deleteMine` and `Db.insertMine`, which read and write only the signed-in user's rows and answer anyone else's as not found, and `requires user, role R` serves a page only to a session with that role; both examples use them, and the mutation operators `scope dropped` and `role dropped` check that their tests notice (chapters 6, 10 and 13). The same rule holds for any session key: `@partition org` on a column, a key `org … via Membership` that the runtime sets only to an org the user is a member of, `requires user, org` and `choose org` on the pages, and `silo org { … }`, which keeps each org's tables in a database of its own, opened and checked when first used, with the compiler refusing a `Task` that writes to two databases; `examples/workspace` is built on them (chapters 6, 8 and 14). `alder repl` keeps a session of `let`s and evaluates expressions, queries and tasks against the app, re-checking when its files change (chapter 11). Every app has a design system, `alder-ui`: a stylesheet and twelve `al-` elements (cards, fields, buttons, tables, badges, alerts, pagination, layout), checked against its manifest like any custom element and served by every build at `/static/al/al.css`; `alder new` and both examples use it (Appendix C). `alder migrate` writes the app's migrations from a change to its tables, and the app applies them when it starts, keeping the data; both examples have them (chapter 8). An app ships with one command: a `deploy` declaration in `App` names its environments (a Linux box over SSH with Caddy, a Fly.io app, a Render service, or a script), and `alder deploy production` runs the gate (check, build, tests, the mutation score against a floor), plans the migrations against the live database and refuses one that drops data without `--allow-data-loss`, uploads, backs up, migrates, starts the new build beside the old one and switches only when the new build answers with its own build id; `alder status`, `rollback`, `logs` and `restore` read the state kept at the target, the runtime streams the database to S3, and `alder ci init` writes the GitHub workflow that runs the same commands, with a preview per pull request (chapter 16). A capability's Go adapter lives in a package named by the compiler, `adapters/<module's first segment>/` with `func <rest of module><Capability>()`; `alder build` generates the wiring and lists every missing adapter with the exact package and function to write (`alder test`, `eval` and the REPL leave a missing one unwired, with a warning, so an app can be tested with fakes first), and a production build carries no test code (chapters 7 and 11). The reference
describes the language as currently specified; the rationale chapter records
what experiments have shown and what is still open.
