# Fill a typed hole with a model: the `Fill with AI` code action and `alder fill --ai`

Design for [tapegram/alder#46](https://github.com/tapegram/alder/issues/46). From the M6b hand test
(2026-10-19): editor-generated code leaves typed holes (`?clear`, `?expected`), and the user doubted
they help a human "unless we then follow up with an ai generating it". Everything marked **(call)**
is the author's decision, not the user's.

## Intent

`alder fill` today takes an expression on standard input and writes it only if the app checks; the
expression comes from a human or an agent, and nothing in the repository calls a model. The book
(chapter 15, "AI only in typed, checked bodies") already argues that a model should write exactly
this: one expression, for a type the checker computed, checked before it lands. This design puts
that loop behind one code action on a hole in the editor and one flag on the CLI, with the same
check, the same refusals and no new structure for the model to get wrong. E11's second run shows the
cost of leaving holes to a later step: five rounds ended on `alder test` refused for `?expected` or
`?afterLogin`.

## Goals

1. On a hole, Neovim's code-action menu (`gra`) offers `Fill ?delete with AI (Task Nav)`; choosing
   it fills the hole in the buffer, as one undoable edit, only when the result checks.
2. The model sees enough to write the expression on the first try most of the time, and the
   checker's errors on the retries; it never sees more than the user's own project.
3. The whole loop runs and is tested without a model: a command backend doubles as the fake.
4. After a generator is applied in the editor, the cursor lands on the first hole it left (the
   issue's option 1), so the fill is one `gra` away.

## Non-goals

- A placeholder arm instead of a hole (the issue's option 2); the hole stays the one shape.
- A chat, a prompt box, or a fill of anything but a hole (`fill --decl` stays human/agent only).
- Any provider but the Anthropic API and a local command; streaming; a model picker in the editor.
- `alder new msg --no-button` **(call)**: out. The button is the cheapest sender, it is what makes
  the generated test run, and it is one line to move; a message without a sender is dead code the
  checker cannot flag.

## Anti-goals

- The model editing anything but the hole's text. It returns an expression; `generate.Fill` places
  it, adds imports, and `Apply` formats and checks, exactly as for standard input.
- Writing to disk from the server, or an edit the client cannot refuse: the edit is versioned.
- A key or prompt in any log by default.

## The backend and its configuration

A backend is `Complete(ctx, system, messages) (text, error)`. Two exist **(call)**:

| variable | meaning |
|---|---|
| `ALDER_FILL_COMMAND` | when set, the backend: run with `sh -c`, the prompt as plain text on standard input (system prompt, blank line, the conversation so far), the expression on standard output; a non-zero exit fails the attempt with its standard error. `claude -p` works as is; a script is the test fake. |
| `ANTHROPIC_API_KEY` | otherwise the Anthropic Messages API, `POST /v1/messages`, over `net/http` as `internal/deploy/render_api.go` does (no SDK: `go.mod` has one dependency and the fake needs the interface anyway) **(call)** |
| `ALDER_FILL_MODEL` | default `claude-opus-5-5` **(call)**; `claude-sonnet-5-5` and `claude-haiku-5-5` are the cheaper current ones |
| `ALDER_ANTHROPIC_API` | base URL, default `https://api.anthropic.com` (the test server), as `ALDER_RENDER_API` |
| `ALDER_FILL_REFERENCE` | optional: a file prepended to the system prompt, e.g. `site/reference.md` (the agent reference, 230 KB); cached |

Request shape: `model`, `max_tokens: 4096`, `system: [{text: <card>, cache_control: {type: ephemeral}}]`
(the reference, when set, as a first block with its own `cache_control`), `messages` user/assistant
alternating; no `thinking` field (adaptive by default on the 5.5 family, absent on older ones) and
no `effort` **(call)**: a fill is short. Headers `x-api-key`, `anthropic-version: 2023-06-01`. A
`stop_reason` other than `end_turn` fails the attempt without a retry (`refusal`: "the model
declined"; `max_tokens`: "the answer did not end"). No fallbacks beta **(call)**: a declined
expression is reported like any other failure. The key is read from the environment only; the
server inherits the editor's, so an exported variable in the shell that starts Neovim is enough.
Neither backend configured: the action is still offered **(call)**, so the feature is discoverable,
and running it says `alder fill: set ANTHROPIC_API_KEY, or ALDER_FILL_COMMAND, in the environment
the editor was started from`.

## The prompt

`internal/fill/card.md`, embedded, is the system prompt: ~150 lines written for this job
**(call)** (not the 230 KB agent reference, which is generated by Python from the book and is not
checked in): what a hole is, expression syntax (blocks, `let x <- task`, `match`, `\a -> …`,
records, `{if … then … else …}`, lambdas take `\`), the `Task`/`Nav`/`Db`/`Test` idioms that holes
in generated code need, and the rules: one expression, no fence, no signature, no prose, name only
what the context lists, leave a `?hole` for what you cannot write.

The user message, built by `fill.Prompt(p *generate.Program, h generate.Hole)`:

1. `Fill the typed hole ?delete in update.Delete of module Replies.Show (app/Replies/Show.alder).
   It must have type: Task Nav`, then the comment lines directly above the declaration (the
   generated test's "Fill ?expected with …").
2. The module's source, whole, in a fence (the hole is in it as written).
3. `Names in scope`: one `name : Type` line per binder at the hole (`scopeAt`), per top-level value
   of the module, and per exported value and type of each app module the file imports, as hover
   prints them; the ones whose type fits the hole first (`completion.fits`), capped at 200 lines.
4. `Standard library`: the signature files (`stdlib/*.alder`, 15 KB in all) of the modules named
   in the hole's type or in the module's source, plus `Task` and `Prelude` always and `Test` in a
   test; comments kept.
5. `Reply with the expression only.`

A retry appends the assistant's answer and a user turn: `The checker refused it: <the errors as
alder check prints them>. Reply with a corrected expression only.` A `generate.Fill` refusal (not
one expression; several holes named) is a checker error for this purpose.

**What leaves the machine**: the card; the one module's source; the names and types above (not
the other modules' bodies); the stdlib signatures; the hole's address and relative path; on
retries, the checker's messages, which quote lines of that module. Never: other modules' bodies,
`migrations/`, `.env`, deploy files, scratch files, anything outside the root, the key. With the
command backend nothing leaves at all. `alder fill <address> --prompt` prints exactly what the
first attempt would send and sends nothing; with `ALDER_LSP_LOG` set the server appends each
request body and answer to that log (no headers).

## The loop: `fill.Run`

`fill.Run(ctx, backend, dir, address, hole, report) (*fill.Result, error)`, in a new package
`internal/fill`: `generate.Load(dir)` → `Prompt` → `Complete` → strip one surrounding code fence and
whitespace → `generate.Fill` → `generate.Apply(dir, edits, Options{DryRun: true})`. The result
checks (no errors; holes allowed, listed) → `Result{Expression, Edits, Files, Imports, Holes,
Attempts}`. Otherwise retry, **three attempts in all (call)**, each with a 120 s context
**(call)**; `report(Attempt{N, Why})` runs before each attempt after the first so a caller can show
"attempt 2: E0003 expected Task Nav, got Task Unit". After the third refusal, or on a backend
error, `Run` returns `*fill.Failure{Expression, Errors, Why}` wrapping the last refusal: the caller
shows the last expression so the user can paste and fix it. `Run` never writes: the CLI applies the
returned edits for real, the server turns `Files` into text edits.

## The CLI

```
alder fill <Module>.<decl>[.<arm>] (- | --ai | --prompt) [--hole ?name] [--dir app] [--json] [--dry-run]
```

`--ai` runs the loop on the app on disk and then writes as `fill` does (`edited …`, the diff,
`added import …`); each retry prints `alder fill: attempt 2 of 3: <first error>` to standard error.
A failure prints the errors, `the model's last expression:` with it, and
`alder fill: the result does not check after 3 attempts: nothing was written`, exit 1. `--json`
adds `"expression"`, `"attempts"`, `"model"`. `--prompt` prints the prompt and exits 0. `-` with
`--ai` or `--prompt`, or `--ai` with `--decl`, is a usage error (exit 2). `help --json` lists the
flags; the agent reference's `fill` line is unchanged (an agent writes the expression itself).

## The editor

**Code action.** On a hole of the current build (`hereCtx`'s `Hole`, and the cursor's line fresh as
for the generator actions), `codeActionReq` adds, before the generator actions:
`{title: "Fill ?delete with AI (Task Nav)", kind: "quickfix", diagnostics: [the W0002],
command: {command: "alder.fill", arguments: [{uri, version, address, hole}]}}` **(call)**:
quickfix, attached to the hole's hint, so every editor lists it with the hole and before the
generators. `executeCommandProvider` lists `alder.fill`: the server runs it, unlike
`alder.generate` (R8). It is offered only when the client declared `workspace.applyEdit`
**(call)**, since the result has no other way back; `initialize` records `workspace.applyEdit` and
`window.workDoneProgress` from the client's capabilities (new fields of `initializeParams`).

**Command.** `workspace/executeCommand alder.fill` (slow worker) validates the arguments, refuses
with `window/showMessage` (Warning, `alder fill: …`) when a fill is already running **(call: one at
a time per server)**, then starts a goroutine under `s.bg` (stopped by `s.stop`, like scratch runs)
and answers `{"started": true}` at once, so previews and plans are not blocked for a minute. The
goroutine: `Materialise(s.rootReal, s.docs.overlay())` as `dryRun` does → `fill.Run` with a backend
from `Options.Fill` → on success, `workspace/applyEdit` with `documentChanges: [{textDocument:
{uri, version: <the version of the hole's document when the fill started>}, edits}]`, `label:
"alder fill ?delete"`; `edits` are one `TextEdit` per changed hunk of `diffLines(before, after)`
(new `generate.LineEdits`), so the hole's lines and an added import are two edits, and an
unformatted file gets its formatting hunks as a generator apply does today. Neovim applies a
versioned edit as one undo step and refuses one whose buffer is newer; the server reads `applied`
and, when false, shows `alder fill: app/Replies/Show.alder changed while filling; the expression
was: …`.

**Progress.** With `window.workDoneProgress`: `window/workDoneProgress/create`, then `$/progress`
begin `alder: filling ?delete : Task Nav` (`message: claude-opus-5-5`), report `attempt 2 of 3:
E0003 …`, end. Neovim shows it in `vim.lsp.status()` (AstroNvim's statusline, fidget, noice);
without the capability, nothing is shown until the end **(call)**. **Failure**: `window/showMessage`
Warning with `fill.Failure`'s text, the errors and the last expression; a timeout reads `alder
fill: no answer in 120 s (attempt 2 of 3)`. There is no cancel in this issue **(call)**: a fill ends
by itself within 3 × 120 s, and editing meanwhile only makes the edit refused.

**Server → client requests** are new: `s.request(method, params) (json.RawMessage, error)` with a
pending map keyed by id, filled by the reader's "a response" case (today a no-op); the test client
gains a `requests` channel and `answer(id, result)`.

**Cursor to the first hole (option 1).** `apply.lua`, after `edit()`: when `plan.holes` is not
empty, open the first hole's file (it is one of the plan's files) and put the cursor on its
`line`/`col`; the notice becomes `alder: applied new msg: app/Posts/Index.alder (2 holes)`. No key,
no plugin code for the fill itself: `gra` on the hole is the whole flow, as the user asked for
shared surfaces. `alder.nvim`'s README gets one paragraph (the action, the variables, the
statusline progress).

## Left to the builder

- The card's exact text, within the rules above; the builder reads chapter 5/6/10's idioms for
  `update` arms and tests and writes them in the card's own words.
- The 200-line cap's order after the fits (alphabetical is fine).
- Whether `fill.Run` takes `generate.Load` as a function for tests, or the tests build apps on disk
  as `fill_test.go` in `internal/generate` does; the latter matches the repository.
