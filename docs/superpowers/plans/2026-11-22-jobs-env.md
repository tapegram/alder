# `alder jobs --env` Implementation Plan (#285)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `alder jobs` lists, retries (`retry <id>`, `retry --dead`) and runs (`run <Kind>`) the
jobs of any deployed environment (Ssh with a file or Turso, Fly, Render), with the local
command's output, a confirmation and the deploy lock on writes.

**Architecture:** The operations stay `rt/jobs/admin.go`'s. A new maintenance task of the app's
binary, `--jobs`, runs them where there is a box or a machine (Ssh through `builds/<id>/run`, Fly
through the Machines API's `exec`) and prints JSON lines; on Render the CLI opens the shared Turso
database and its silo children itself. `cmd/alder/jobs.go` is split into sources (local files,
Turso stores, the binary's JSON) that gather a `jobsReport`, and one printer, so the local and
remote output are the same lines.

**Tech Stack:** Go (CLI, runtime, generator), SQLite (`modernc.org/sqlite`), Turso over Hrana,
the deploy fakes (`internal/tursofake`, `renderfake`, `fakeFly`, the loopback Ssh box), markdown
(`book/`).

**Spec:** `docs/superpowers/specs/2026-11-22-jobs-env-design.md` (at 6fa2e8ee). Read it first.
Its eight "Decisions" are ruled: every recommendation is accepted (Turso directly on Render;
confirm + `--yes`; writes under the deploy lock; Render's `run` checked against the local app;
a silo retry writes a silo hint; `--env` is a flag; Fly tested through its fake; no `--silo`).
A task names the spec section it implements; that section is part of the task's requirements.

**Ordering with #283** (job controls, `docs/superpowers/specs/2026-11-22-job-controls-design.md`,
planned at the same time): both change `rt/jobs/admin.go` (#283: `Retry` takes `cancelled`,
`Listing.Cancelled`, the `StateError` wording), `rt/jobs/table.go` (`Row` gains `Priority`; here
`Row` gains json tags), `rt/jobs/run.go` (`Kind` gains `Priority`; here `Params`),
`internal/gen/jobs.go` (the `Kind` literal), `rt/db/migrate.go` (#283 bumps `jobsSchema` to "2";
here it is exported), `cmd/alder/jobs.go` and `jobs_test.go` (#283: `cancel <id>`, priorities,
cancelled counts; here the gather/print split), `book/17-jobs.md` and `CHANGELOG.md`. Neither
depends on the other's behaviour. Ruled 2026-11-22: all three #283 PRs land first, then this plan;
Task 5's gather/print split moves #283's `alder jobs cancel` onto the split printer. This plan rebases and keeps the other's additions:
a `Priority` field on `Row` gets `json:"priority"` (Task 2's round-trip test catches a missing
tag); the local printer's state list gains `cancelled` after `dead`; Task 9's schema check reads
`db.JobsSchema`, so it follows #283's bump with no edit. Merge one after another, never in
parallel branches (memory: everything on main).

## Global Constraints

- Four PRs, each from a short branch off main, green on its own, merged before the next starts:
  PR 1 = Tasks 1–4, PR 2 = Tasks 5–7, PR 3 = Tasks 8–9, PR 4 = Task 10.
- No new Go dependency; `go.mod` does not change.
- Nothing new is installed at any target and no new credential is read on this machine: Ssh uses
  its ssh and the box's environment file, Fly `FLY_API_TOKEN`, Render `RENDER_API_KEY` and
  `TURSO_API_TOKEN` (already required by `Render.Connect`). The deploy commands read this
  machine's environment only through `deployEnv` (`cmd/alder/deploy.go:50-101`).
- No value of any environment and no job's params are printed: `Row.Params` is `json:"-"`.
- Exit codes (spec §1): 0; 1 for a refused operation (unknown id, job not dead, key held,
  orphaned silo), the deploy lock held, a target not reached, an environment not deployed, a
  build older than `--jobs`; 2 for usage, a missing declaration or environment, a Script target,
  a store that cannot be read, a write not confirmed, `run` of a kind the build lacks or one with
  parameters.
- Copy fixed by the spec, verbatim:
  - `--db takes a file; --env an environment`
  - `jobs at <Describe()>, build <id>, and N silo databases:` (the `, and N silo database(s)`
    part as `siloCount` words it today; absent with no silo)
  - `queue job <id> again at <Describe()>, due now? type yes: `
  - `queue the N dead jobs at <Describe()> again, due now? type yes: `
  - `queue a run of <Kind> at <Describe()>, build <id>, due now? type yes: `
  - `not confirmed: nothing was queued (pass --yes to confirm without a terminal)`
  - `environment <env> is not deployed yet: no build serves there`
  - `queued for build <id>; a kind that build does not declare waits for one that does`
  - `silo <key>/<value> is orphaned: nothing runs there (alder silos prune)`
  - `no jobs table at <Describe()>: the app declares no job, or build <id> was made before background jobs`
  - `the jobs table at <Describe()> is schema N, newer than this alder's M: upgrade alder`
  - the silo retry note gains `; a \`--jobs-only\` worker reads the silo hint within a poll`, and
    remotely says "a running build's workers" for "a running app's workers".
- The JSON lines are an interface between two alders of different ages: unknown fields are
  ignored (`encoding/json`'s default), and every field this plan adds is `omitempty` except
  `silo`.
- Verify every behaviour claim written into help text, the book or an error message against the
  Go and cite `file:line` in the task report.
- Scoped tests per task; `go test ./...` once before each PR is opened. Box tests skip under
  `-short`, as `TestDeploySsh_Silos` does.
- After each merge: `go install ./cmd/alder` (memory `alder-reinstall-after-merge`).

## Review Focus

Inputs the spec implies that no headline test would meet. Each has a test in the task named.

1. **A box whose environment file sets `ALDER_LOG_FORMAT=json`**, so a line the binary writes to
   stderr (merged by `2>&1`) starts with `{` but is not a report line. The decoder treats a `{`
   line that does not decode, or has none of the report's keys, as a message, and the listing
   still prints. Task 2.
2. **`retry --dead --env` with no dead job.** No question is asked, no lock is taken, `no dead
   job`, exit 0 — also without a terminal and without `--yes`. Task 7.
3. **A write that is not confirmed, or confirmed and done, leaves no deploy lock behind**: a
   second command right after takes the lock. Task 7.
4. **Render with a service but no shared database** (a first deploy that failed before its
   Turso step). Every operation is "not deployed" (exit 1), and the fake Turso has no new
   database afterwards: `Render.Lock` creates the database (`render.go:291-293`), so the CLI must
   find it before it locks. Task 9.
5. **A dead job whose error spans lines, or carries a schedule tick, in a silo**, read through
   the binary: the remote listing prints the same row line as the local command (`first line …`,
   `(the schedule tick of …)`, `(in silo org/42)`). Task 7 compares the two outputs line for
   line.

Spec points the plan settles (the code differs, or the spec leaves a choice):

- **No `maintain` goldens exist**; Task 4 extends `internal/gen/caps_test.go`'s source checks and
  builds a binary as `TestOptions_AlderJobs` does.
- **`refused` is always an array.** The spec has a string for `retry <id>` and an array for
  `retry --dead`; one shape (`"refused": ["…"]`) serves both and the decoder has one field.
- **The old-build sentence has no "(before <version>)"**: the release that carries `--jobs` is
  not numbered yet. It reads `build <id> at <env> was made by an alder without \`alder jobs
  --env\`: \`alder deploy <env>\` with this alder, then try again`.
- **Fly runs through `running` + a new `execCode`, not `read`**: `read` goes through `exec`,
  which turns exit 1 and 2 into errors.
- **Render's orphan check needs the app's silo refs and tables**, which the Render target does
  not hold; the CLI computes them from the working tree (as it does for `run`, Decision 4) with
  a new `migrate.SiloDecls` and an exported `db.Orphans`.
- **The "silo under maintenance" note** is printed on the binary path only (the binary knows the
  build's schema); on Render the CLI has only the working tree and prints no such note.
