# M10: Distribution — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Install Alder with one command and build, test and run an app without a checkout: the runtime ships inside the compiler, `alder new` scaffolds a working app, releases are built per platform, and the book and a docs site say how.

**Architecture:** (1) Embed `rt/**` in the binary and write it into `build/<app>/rt/` with a relative `replace`; `alder version`. (2) `alder new`; LICENSE; README; chapter 1 "Installing". (3) The GitHub repository, CI and release workflows, GoReleaser (binaries, Homebrew tap, container image), the docs site.

**Tech Stack:** Go `embed`, `debug.ReadBuildInfo`, GoReleaser, GitHub Actions, a small Python site builder.

**Spec:** `docs/superpowers/specs/2026-10-12-m10-distribution-design.md` (binding: nothing generated depends on the GitHub path; Apache-2.0; private repo under `tapegram`).

## Global Constraints

- The generated `go.mod` is `module app`, `require alder v0.0.0`, `replace alder => ./rt` (relative); the embedded runtime's module stays `alder`. No generated file mentions `github.com`.
- The embedded file set is checked by a test against `git ls-files rt` minus `_test.go`.
- Both examples and the scaffold build, test and serve from a directory outside the repository using only the built `alder` binary and `go`.
- The existing goldens change only where the `go.mod`/header text changes (explain in the commit); the production Go of the examples is otherwise byte-identical.
- The first build on a clean machine may fetch `modernc.org/sqlite` from the Go proxy; every later build is offline. Documented in chapter 1.
- Outward-facing actions (creating the GitHub repositories, pushing, publishing a container image) are done in Task 3 only, as the user authorised: repository `tapegram/alder` PRIVATE, tap `tapegram/homebrew-alder` private too; no release tag is pushed (the first tag is the user's call); the container image is built locally and not pushed.
- Gate: `gofmt -l $(git ls-files '*.go')` empty; `go vet ./...`; `go test ./... -count=1`; both examples check/build/test; `(cd experiments && python3 -m unittest)`; `go test ./book -count=1`; the out-of-tree build test.
- Commit messages end with the session trailers; stage by explicit path.

## Review Focus

1. **A stale `build/<app>/rt/` from an older compiler**: expected — every build refreshes the directory (adds, replaces, removes), so a file deleted upstream cannot linger and break `go build`. Test in Task 1 (plant a stray file; build; it is gone).
2. **`go install …@latest` binary vs release binary vs checkout**: `alder version` prints a sensible string in all three (module version / `devel+<commit>` / `(devel)`); the generated header carries it. Test in Task 1 (checkout and a `go install` from the local path with `GOFLAGS=-mod=mod`) and Task 3 (snapshot release binary).
3. **`alder new` inside another Go module** (as `examples/` is): the scaffold gets a `go.mod` that keeps it out of the parent module (the examples' trick); outside any module, no `go.mod`. Test in Task 2 (both placements).
4. **The scaffold and chapter 2 drift**: expected — the verifier builds the scaffold with the built binary and compares its files with chapter 2's `part=` blocks, so a change to either fails `go test ./book`. Test in Task 2.
5. **CI on a clean runner**: the workflow installs Go only, builds the binary, runs the gate incl. the examples (which fetch modernc once) and the out-of-tree build; a failure there is the signal that something still depends on the checkout. Test in Task 3 (the workflow must be green on the first push).

### Task 1: Embed the runtime; `alder version`

**Files:** create `internal/dist/embed.go` (`//go:embed` of `rt/**` is not possible from `internal/`: place the embed in `rt/dist.go` at the module root? — Go embeds relative to the package directory and cannot cross into parents; ruling: a package `dist` at the REPOSITORY ROOT? No: put `embed.go` in a new top-level package `runtime` (`alder/runtime`) is also a sibling. Correct approach: a `go:generate` step that copies `rt/**` into `internal/dist/rt/` before `go build`? That breaks `go install`. Use the trick the stdlib uses: `stdlib/embed.go` embeds its own directory; so add `rt/embed.go` in package `rt` with `//go:embed *.go db/*.go eff/*.go html/*.go web/*.go datastar/* testing/*.go tether.go …` (explicit list of subdirectories; a test keeps it complete) exporting `var Files embed.FS`, plus the module files `rt/dist/go.mod` and `go.sum` (generated by a test-checked script from the root `go.mod`/`go.sum`, keeping only `modernc.org/sqlite` and its requirements)); modify `internal/buildkit` (`WriteRuntime(dst)`: refresh `build/<app>/rt/` from `rt.Files`, removing stale files; called by `cmd/alder/build.go` and `internal/scratch`), `internal/gen/gen.go` (`goMod()` → the relative replace; drop `Options.RepoPath`), `cmd/alder/version.go` (`alder version`), the generated header, goldens (`go.mod` text), tests: the embed-completeness test (`git ls-files rt` minus tests ≡ `rt.Files`), the refresh test (RF1), the out-of-tree build test (copy an example to a temp dir, run the built binary from a `PATH` with only it and `go`, build, test, serve `/`), RF2 version strings.
