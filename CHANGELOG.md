# Changelog

Every release of alder, newest first. "Breaking" lists what stops an app that compiled
with the previous release, each with what to do.

## Unreleased

### Breaking

- The jobs table moves to schema 2 when the app opens the database (the `priority` column and the index `_alder_jobs_claim`, which replaces `_alder_jobs_due`), once, on the shared file, each silo and Turso. A build older than this one that claims jobs beside or after it fails every claim (its `RETURNING *` returns a column it does not read): a warning, then one a minute, and `"jobs": "stalled"` on `/_alder/health` after five minutes, until it is replaced. Roll the new build out to every instance that runs workers, since an old worker keeps failing until it is replaced, and expect the same after a rollback to an older build (#283).
- `Job.State` has a fifth constructor, `Cancelled`, so an exhaustive `match` on a `Job.State` stops compiling until it has a case for it. Add a `Cancelled ->` arm to a `match` on `Job.State`. A build older than this one fails a `Job.status` of a cancelled job (its state is none it knows), so a page that polls one errors until that build is replaced (#283).
- `job` is a reserved keyword (it opens a job declaration), so an identifier named `job` stops parsing. Rename it (#168).
- `Job` is a Prelude type an app writes (`Job.enqueue` takes one), so a type, table, form or union of your own named `Job` is E0012. Rename it, for example to `JobType` (#168).
- A session field that is a `Text.Secret` (or a `Maybe Text.Secret`) is E0048: the session cookie is signed, not encrypted, so the user can read it. Keep the secret in a table and store the row's id in the session (#254).
- A write route's handler is named after its method: `Save.put`, `Create.post`, `Toggle.patch`, `Remove.delete`, not `Save.update` (#308). A handler still named `update` is W0013, with a quick fix at each site; `alder fmt` renames the declaration and every reference to it, in the whole project at once. `alder generate` writes method-named handlers, and `alder regen` keeps the `update` name of an app that still declares it. Run `alder fmt` over the app.

### Added

- `requires` clause on a value's signature: `shown : Query Int requires org` (or on the next line, indented) states the session keys the value needs, in any module. The checker compares it with what the body needs: a route-module or job-module helper that needs a key without the clause is W0014 (callers see only the clause, so the need now shows at the use), fixed by `alder fmt`, which inserts the clause in the session's key order across the whole project; a key the clause names that the body never needs is W0015; a helper without a clause in a module with no route or job is E0026; a clause on a route's member or on `Job.run` is E0043 (write it on the route, or `silo k` on the job; a job never has `user`). `alder generate` and `alder regen` write the clause. The language server shows the clause in hover (and the inferred key for a W0014 helper), completes the keys after `requires` and offers the W0014 fix as a quick fix; tree-sitter and semantic tokens highlight it (#310).
- A value that needs a session key (it uses `Db.mine`, `Db.scoped T` or an unscoped operation on a siloed table, or refers to a value that does) may live in a module with no route or job, a table's module included, when it states the key with a `requires` clause (#310): `count : Query Int requires org` in `Table/Member.alder` is no longer E0026 ("…: `Table.Member` declares no route"); without the clause it is still E0026. The need is checked where the value is used: in a route's member without the key, a job's `run` without its `silo`, or a fake (also a fake's reference to a value of its own module, which was not checked). E0026 names the first helper a need comes through, ``…uses `Db.scoped Reviewer` (through `Table.Reviewer.current`), which needs a route that `requires org`: `Index` does not``, and E0031 names the helper a write is reached through, ``…and `AuditLog` (shared, through `Audit.record`)`` (#310).
- SVG in views: the elements `svg`, `g`, `path`, `line`, `polyline`, `polygon`, `rect`, `circle`, `ellipse`, `text`, `tspan` and `desc` (`<title>` inside an `<svg>` names the drawing), so a view can draw a chart or an icon on the server without `Html.unsafe` or a script. Their attributes are all `Text`: `viewBox`, `preserveAspectRatio`, `xmlns`, `x`, `y`, `x1`, `y1`, `x2`, `y2`, `cx`, `cy`, `r`, `rx`, `ry`, `d`, `points`, `width`, `height` where the element takes them, and the paint attributes `fill`, `stroke`, `stroke-width`, `stroke-dasharray`, `stroke-linecap`, `stroke-linejoin`, `opacity`, `fill-opacity`, `stroke-opacity`, `transform`, `text-anchor`, `dominant-baseline` and `font-size`, with the global ones, `data-*` and `aria-*`; any other attribute on an SVG element is E0002 (`` `<rect>` takes no attribute `href` ``; one in the wrong case, such as `viewbox`, adds "did you mean `viewBox`?"), and so is an HTML or custom element directly inside an SVG element (`<title>` apart), such as a `<span>` in a `<text>`. An `id` inside an `<svg>` is not a region: a change to a shape patches the whole `<svg>` or a region around it, since a patch is parsed as HTML and would take the shape out of the drawing. `viewBox` and `preserveAspectRatio` keep their case in the page and in a test's parsed `Doc`, a test selector's attribute names match in any case (`[viewBox]`), and `ellipse`, `text`, `tspan` and `desc` are selector tags (`Test.count "svg polyline" page.doc`). Hover and completion in editors list them, and attribute completion replaces a typed name with capitals or digits whole (`viewB`, `x1`). Book chapter 5, "SVG" (#306).
- `Job.cancel id : Task Bool` takes a job back: `True` when it was queued or running and is now `Cancelled` (a fifth `Job.State`, kept a week and retried by hand like a dead one), `False` for no such job, a finished one or a schedule's queued tick. A running attempt is cut off at its next step in this process and within a second (the workers' poll) in another, and its writes are undone; its log line reads `job K ID cancelled 120ms attempt 1`. The cancel is in the `Task`'s transaction (a cancel of a shared-store job from a silo-bound `Task` is its own statement). The Jobs page has a Cancel button on queued and running jobs, and `alder jobs cancel <id>` does the same (#283).
- `priority N` on a `job` declaration (an integer, 0 by default, negative allowed; a float is E0050): the workers and `Test.work` claim a due run of a higher priority before a lower one, then the oldest due. It is strict (no ageing) and orders one store's queue; a schedule's tick takes its kind's priority. `/_dev/jobs` and `alder jobs` show `priority N`, the queued list is in claim order, and `priority` is in `/_dev/jobs.json` (#283).
- `Job.Id` is a brand of `Text`, so a route can take `{ job: Job.Id }`, which lets a page that starts a job redirect to a page that shows it with `Job.status`, and a table column can carry one; and `Job.enqueueIn ms job`, which queues a job not before `ms` milliseconds from now (#283).
- Background jobs (#168): a module declares a job with `job Name = { … }` and its arm `Name.run : Name.Params -> Task Unit`, with the options `every "1h"`, `cron "0 3 * * *"`, `retries`, `timeout` and `silo`; `every`, `retries`, `timeout`, `silo` and `cron` are checked: a `cron` expression has five fields (minute, hour, day of month, month, day of week) of numbers, `*`, `,`, `-` and `/`, in UTC; an unreadable one is E0050 naming the field at fault (one without five fields says how many it has), and so is a restricted day of month with a `*` day of week when none of its days exists in the months listed (`0 0 31 2 *`; `0 0 31 2 1`, with both day fields restricted, runs on Mondays in February). `Name { … }` builds a `Job`, and the `Job` module puts it on the queue: `Job.enqueue`, `Job.enqueueAt` (not before a time), `Job.enqueueOnce` (unless one of its kind with that key is queued or running) and `Job.status`. A job is stored in the `Task`'s transaction, so a failed `Task` drops it. In tests, `Test.jobs` lists every job with its status (queued, running, done or dead) and `Test.work` runs the due ones. A parameter that cannot be stored is E0049, and a job's options the rules refuse (two schedules, parameters on a scheduled job, an unreadable or out-of-range `every` or `timeout`) are E0050. Jobs run in the app's own process: `ALDER_JOBS=N` workers start with the app (default 4; `0` starts none; a bad value stops it before it serves), each claiming the oldest due row and running it as one transaction with the row's mark, and a failure is retried with a backoff until the job is dead. With `ALDER_METRICS`, `alder_jobs_total` (by kind and outcome), `alder_job_duration_seconds`, `alder_jobs_running` and `alder_jobs_queued` are exposed, and `/_alder/health` of an app that declares a job carries `"jobs": "ok"`, `"off"` or `"stalled"` (it never changes the status). Under `alder run`, a rebuild stops the old app with 10 s before it is killed (was 5 s), so its running jobs are queued again for the new one. `every` and `cron` schedules fire: a scheduled job has one queued tick, made when the workers start and at each housekeeping (every minute), due at the next minute its `cron` matches (UTC) or `every` later, put on the interval's grid from midnight UTC when the interval divides a day (`every "1h"` runs on the hour). Running a tick queues the next one, so a tick missed while the app was down runs once, late, not once per missed time, and a failed tick is retried like any job. A changed schedule applies at the next housekeeping, or after one more tick of the old one: a queued tick due later than the new schedule's next two times moves to the first of them, and a job whose `every` or `cron` was removed loses its queued tick. A queued tick of a job the build no longer has is deleted once it is more than a day past its due time (it was a day after it was made, which deleted a new weekly job's tick after a rollback to a build without that job; a tick not yet due is now kept). In tests, the first `Test.work` of a test makes the ticks from the test's clock. In an app with silos, a job is stored in the store its `Task`'s writes bind it to (the silo of the org a `requires org` route writes the tables of, else the shared store: a route that only queues a job writes nothing, so its job is in the shared store), and a `silo k` job runs bound to the silo its parameter names. The workers look for jobs in the shared database and in every silo that had jobs when they started (one pass that opens each silo file, or Turso database, read-only, without the migration check, and closes it again; none stays open) or that a job was queued in since, until it has had no job queued or running for an hour; their looks do not keep a silo open, a closed silo is opened again only when one of its jobs is due, and a silo under maintenance is not looked in. `alder_jobs_queued` and the `"stalled"` check count those silos' jobs too. On Turso the jobs table is created by `alder deploy`'s migration run and when the app opens the database. A database whose claims keep failing is one warn line, then at most one a minute, and one line when it works again. `app --jobs-only` runs the app's job workers and no listener (`ALDER_ADDR` is ignored, and there is no `/_alder/health`): `ALDER_JOBS` defaults to 8 in this mode, and `SIGINT` or `SIGTERM` stops claiming, gives the running jobs 5 s, then cancels them and queues them again before it exits 0. A serving app stops claiming as soon as it gets `SIGINT` or `SIGTERM`, and the requests in flight and the running jobs share the same 5 s (#288). On Turso it exits 1 when the database is behind the build, as serving does, and when a newer build migrated the database it runs no job and reads the database's schema again every 10 s until it matches. An app run with `ALDER_JOBS=0` that queues a job in a silo records the silo in the shared database (`_alder_jobs_silos`) before the `Task` commits, and the `--jobs-only` workers read those records once a poll (1 s), a read that wakes an idle worker, so with a worker idle the job starts within a poll. A Render environment's `workers: N` (a whole number of at least 1, else E0030) moves the jobs to a worker service: `alder deploy` creates, or scales and rolls, a background worker `<service>-worker` running the same image as `app --jobs-only` on N instances, sets `ALDER_JOBS=0` on the web service, and waits for the worker's deploy to be live after the web health check; `alder status` lists both services and `alder logs <env> --worker` reads the worker service's log (a usage error naming `workers:` on an environment without it). `alder deploy init render` refuses an app with `workers` (worker machines need a shared Turso store, which `alder deploy` sets up and `render.yaml` cannot), and an environment without `workers` refuses every Render command (`deploy`, `status`, `logs`, `rollback`, `restore`) while a `<service>-worker` service still exists, until it is deleted or suspended. `alder jobs` reads the app's dev database (`build/<app>/dev.db`, or the file `--db` names) and the silo databases beside it (`silos/<key>/*.db`), and prints the count of jobs in each state, each scheduled job's next tick and the dead jobs with their attempts and the first line of their error; `alder jobs retry <id>` queues a dead job again, due now, with its attempts at 0 and its error cleared (a retried schedule tick runs once and queues no next tick), `alder jobs retry --dead` does so for every dead job, and `alder jobs run <Kind>` queues a run of a job without parameters, due now, apart from its schedule (a job with parameters is a usage error naming them). It changes the file directly: a running app's workers find the job at their next look (in a silo, while the silo is in their active set, or after they restart). `alder jobs [retry <id> | retry --dead | run <Kind>] [dir] --env <name> [--host name] [--yes]` does the same against an environment of the `deploy` declaration, with the same lines: at an Ssh box (a database file or `database: Turso`) and on Fly, the current build's executable runs the operation there (its `--jobs` task, over the shared database and every silo database), and on Render this machine opens the shared Turso database and its silo databases; the header names the target and the build. Listing asks nothing and takes no lock; `retry` and `run` ask first (`--yes` answers; without a terminal and without `--yes` nothing is queued, exit 2) and take the deploy lock where the target has one (an Ssh box or Render; Fly has none), so at a box and on Render they are refused, naming the holder, while a deploy, rollback or restore runs. `run <Kind>` is checked against the deployed build's jobs; on Render against the working tree's, and a kind the serving build does not declare waits queued for one that does. On Render a jobs table a newer alder made is refused (exit 2), a shared database without one lists zero counts and says so, and a retry in a silo whose key row is gone is refused (`silo org/42 is orphaned: nothing runs there (alder silos prune)`, as at a box). A retry in a silo also records the silo in the shared database, so a `--jobs-only` worker finds the job within a poll. A build made by an alder without `alder jobs --env` is told apart and refused (exit 1: deploy it again with this alder); `cancel <id>` works on a local database only. Under `alder run` (development mode, `ALDER_DEV=1`), the dev server has a Jobs page, `/_dev/jobs` (queued/running/dead/last 50 done, next tick per scheduled kind, a job's params (a top-level member named like a secret, such as `password` or `token`, is shown as `••••`), error, attempts, last attempt's trace and the write-lock mark; Retry / Run now; `/_dev/jobs.json`). In editors, `job` and a job's option words (`every`, `cron`, `retries`, `timeout`, `silo`) are keywords in a job's line only (tree-sitter and the server's highlighting) and hover with their documentation; go-to-definition and references reach a job from its constructor and its `run`; `workspace/symbol` lists a job and its `Name.run`; and `alder search` (and `--json`, with `kind` `"job"`) finds a job by name or by its constructor's type, and its `Name.run` as a function. `alder new job <Name> [<field>:<Type> …] [--every D | --cron E] [--into M]` writes a job (in `app/Jobs/<Name>.alder`, or appended to `--into`'s module), a `run` that logs and succeeds, and a test that queues and works it; a scheduled job's test sets the clock a minute before its first tick (an `every` that does not divide a day, such as `7m`, has no grid to stand before, so its test starts the clock at 2026-03-04 00:00). Book chapter 17, "Background jobs", covers jobs from the declaration to the worker machines, with how the queue works inside.
- `alder-tui` has a Jobs screen (tab 6): the counts by state, each schedule's next tick and the queued, running, dead and last done jobs, read from the dev server's `/_dev/jobs.json`, with `r` to retry a dead job and `n` to run a queued one now; Logs sets a job attempt's line apart with a cyan `job <Kind>` (#284).
- Book appendix D, the standard library reference, generated from the doc comments in `stdlib/` and held current by a test (#227).
- `alder search <query>`: search the standard library and the app by name, by module (`Text.`) or by type (`Text -> Int`, `: List Text`, `_` as a wildcard), with `--json` (#166).
- Language server: `alder/search` and `alder/searchEdit` (search by name or type, and for a picked result the edit and the cursor), `workspace/symbol` for the app's declarations, and a "Search for <type>" action on typed holes for clients that declare `experimental.alderSearch` (#166).
- Language server: `textDocument/documentSymbol`, the outline of a file as hierarchical symbols (functions, values, types with their constructors, jobs with their `run` arm, routes and the other top-level declarations), from the buffer's text (#289).
- Doc comments: a comment above a declaration in the format of a summary sentence, detail paragraphs, examples indented four spaces and a `Book: chapter N, "Heading"` line. Hover shows it with the examples in a code block and the book line, completion items carry it, `alder search` shows the summary in its DOC column, and `alder search --doc` prints the details, examples and book line; `--json` results gain `summary`, `examples` and `book`. `List`, `Maybe`, `Result`, `Text`, `Int`, `Float`, `Bool`, `Dict`, `Bytes`, `Task`, `Query`, `Db`, `Session`, `Notice`, `Response`, `Html`, `Http`, `Url`, `Log`, `Prelude`, `Date`, `Time`, `Random`, `Json`, `File`, `Test` and `Fuzz` are documented: every module and declaration of the standard library has a doc (#119).
- Hover on an operator (`|>`, `??`, `==`, `+`, …), on `<-` in an effect block or on a keyword (`match`, `route`, `requires`, …) shows what it does, its signature when it has one, examples and a book reference; hover on a typed hole adds what a hole is and how `alder fill` fills it (#119).

### Fixed

- Two `alder rollback --restore-backup` or `alder restore` runs within one second kept the database each replaced under one name (`db/app.db.before-rollback-<time>`), so the second overwrote the first's. A second kept file in the same second now gets `-2`, `-3`, … after the time, on SSH (and silo and Turso) targets and on Fly.
- The dev panel and its "Copy as curl" line mask a route's `Text.Secret` form fields and path parameters by type, not only by name (a `pin` field was shown), and a log line masks a `Text.Secret` path parameter. The `Text.Secret` docs now say what is masked and what is not: `Log`, `Json.string`, `++` and a view's text show it in clear (#254).

## v0.2.0 — 2026-11-11

### Breaking

- Routes replaced pages, messages and `Nav` (#160 and its follow-ups). Every request goes to a
  route: a `page` is a GET route, a `msg` is a write route, an update answers `Task Response`
  (`Response.refresh`, `Response.redirect`, `Response.invalid`), and `Html` takes no type
  argument. The removed syntax is E0046, which names the replacement (chapter 6 has the
  rewrite); there is no migration tool. A write route that declares `form F` is sent with
  `<form submit={R}>`: `click={R}` of it is E0045. `alder new page`, `edit page` and
  `remove page` are gone for `alder new route`, `edit route` and `remove route`; `alder new msg`
  is `alder new action` (the old name still works as an alias until the next release). In
  tests, `Answer`'s `Rerendered` is `Refreshed` (or `Rendered r`, with the route), and
  `Test.click` and `Test.submit` take the route (`Test.click (Toggle { id: id })`).
- alder-ui is v0.4 or later (the shadcn look; v0.1.0 shipped v0.3.3). The `--al-*` tokens of
  v0.3 are removed, so your own CSS that uses `var(--al-…)` stops applying, and `[data-theme]`
  and the OS-dark CSS are gone, so dark mode needs the theme script in your Layout's `<head>`.
  Appendix C, "Migrating from v0.3.x", has the steps and the table of removed tokens.
- The standard library gained `Json` (and `Bytes`, `File`, `Fuzz` and `Response`). An app module
  with one of those names is E0017: rename it, or use the standard library's.
- Imports have one canonical spelling (#23). An `import` whose `as` is missing, redundant or
  not the canonical qualifier is E0204, a name written with an imported module's full path
  instead of its qualifier is E0205, and an import with no usable qualifier is E0206. Run
  `alder fmt`, which rewrites the imports and the names (E0206 needs a rename by hand).
- An Int literal that does not fit in 64 bits is an error (E0001); it used to become
  9223372036854775807 (#81). `-9223372036854775808` is writable.
- The body of `<script>` and `<style>` is raw text, as in HTML. A body that is one `{ … }`
  interpolation, or that contains `</script` or `</style`, is E0001. Pass data to a script
  through `data-*` attributes.
- A query string a route cannot parse (a raw `;`, a bad `%` escape) answers 400 naming the
  parameter; it used to reach `load` as if the parameter were absent (#12).

### Added

- `alder lsp`: diagnostics, completion, hover, definition, references, code actions, semantic
  tokens, folding, selection ranges and the generators (`alder/plan`, `alder/preview`); fill
  typed holes with AI from the editor.
- `alder tui`: a terminal UI for a running app (requests, logs, tests, routes, data).
- New commands: `alder fmt`, `alder scratch`, `alder bench` (with N+1 warnings), `alder routes`,
  `alder theme` and the `/_dev/theme` configurator, `alder logs` filters; styled output.
- Standard library: `Json`, `File`, `Bytes`, `Response`, `Fuzz`, `Html.fragment`, `Text.hash`,
  a seeded `Random`, `Url.absolute`, `Test.setClock`.
- Property tests (`Fuzz.forAll`, shrinking, saved failures) and route mutation operators.
- Deploy to Render beside Fly (`alder deploy init render|fly`), a health endpoint, a metrics
  endpoint, an access log and request ids.
- Generators for routes (`alder new route`, `new action`) and the admin on resource paths.

### Fixed

- Migrations are listed by reading the directory, not by globbing it, so an app path with
  glob characters (`[`, `*`, `?`) builds and deploys (#172).
- E0017 says to rename the module or use the standard library's, and its explanation points
  here; a `Text` where a `Json.Value` is expected names `Json.string` and `File.text` (#175).
